How the layers were made to fit

The Brain is built so that a partner can be replaced without touching the Brain: everything that depends on the Twin's naming, units or speed is configuration, not code, and every behaviour is agreed with the partners in the Interface Card.

One contract. The Data Dictionary messages, one example of each in contracts/examples/, JSON Schemas exported by one command, a four-edit rule for any change.

Trust is shared. The Guardian judges; the Brain scales trust by the verdict’s confidence and never learns from an untrusted reading.

One way out. Only the gate signs a call; agents get read-only tools; a valve or the grid needs a person.

Every layer runs alone. The mocks of the Twin and the Guardian ship with the Brain; brain conformance checks a real partner against the same contract.

Partners differ. brain onboard proposes renames and units for a Twin that names things differently and never edits config.

Failure is a state. A silent Guardian, a missing Twin, a spent model quota and an unknown alarm each have a named event and a defined behaviour.

Evidence, not claims. 1,114 tests, 5 Test Book scenarios, 60 held-out variants, a hash-chained log per run, and brain rehearse as the freeze check.

One command. make full builds one image and starts the Brain, both stand-ins, Neo4j and Qdrant.

2. The City Brain

Written by the City Brain team · repository folder triplet-03/brain/ · contract 2026-09-17, Guardian contract 1.0 · key question: “What should we do?”

2.1 Role and goals

The Brain reads the Twin’s live sensor readings, detects incidents (crimes, fires, accidents, jams, floods, grid overloads), asks the Guardian whether each reading can be trusted, chooses a response and carries it out through the Twin’s actuators. It acts only on readings the Guardian has marked trusted, and only through the safety gate, the one component allowed to call an actuator.

With the Guardian team’s contract 1.0 (dashed line) the Twin also feeds the Guardian, and valve, grid, signal and dispatch calls reach the Twin through the Guardian’s audit. Amber dashes: a solver’s answer enters a team’s brief; green dashes: learning.

2.2 Architecture

Figure 2.2 follows one reading through the components of Figure 2.1, in eighteen steps from the Twin to an action and its explanation. Each card names the component, the technology that runs it and, in blue, the brain function that inspired it. The analogy guides the design; the Brain does not model a brain.

Figure 2.2. From a reading to a decision. Amber arrows lead to the gate: reflex proposals reach it at once, and the team’s plan follows through the same gate. A plan the team makes the same way twice returns as a reflex after the sleep phase.

2.2.1 Incident detection

Perception checks the contract version, the HMAC signature, the sequence number and the value ranges, and refuses a bad reading with a code. The Guardian’s verdict, requested with a 2 s deadline, decides whether the reading may count. Forward models learn each sensor’s normal range from trusted readings only. A reading far outside it is flagged as a surprise, and the reflex it would trigger waits for a second source; a Kalman tracker forecasts when a river will reach the flood line. Triage runs the departments’ detectors to open or join an incident, and the workspace gives two incidents at a time the team’s attention, ranked by severity, trust, surprise and urgency.

When an alarm matches no department, an incident has no procedure, or an incident stalls, the Brain emits brain.human.needed and asks a person.

2.2.2 Decision method

Rules (14, in six packs) answer in milliseconds with no model. Agent teams weigh the case: for Police an Analyst, a Tactician and a Chief on LangGraph, using Groq models with --llm and a scripted stand-in otherwise or when the model fails; the other departments use a two-role desk. Solvers compute what should not be guessed: OR-Tools min-cost flow for dispatch, CP-SAT for a perimeter and for load shedding, Dijkstra for a green corridor and the Kalman forecast for floods. They run before the agents and their answers go into the agents’ brief, so a model that never calls a tool still reads them.

Code then verifies the agents’ plan (verify_case, verify_plan, verify_desk) before it reaches the gate.

2.2.3 Choosing an actuator

The Brain picks an actuator in three steps. The incident type decides which department may act and with which actuator; a solver, or the nearest free station, picks the device; and the gate decides whether the call goes out. No other code path calls the Twin.

Figure 2.3. The planning graph for one incident (LangGraph). The solver and the agent team work in parallel, the better plan is kept, a valve or grid call pauses for a person, and each step is checkpointed to SQLite so a run can resume and be replayed.

Station or device

The nearest free station by hop distance, never a quarantined or reserved one. In T16 the Guardian quarantines a station, the gate refuses calls to it with reason quarantine, and another station is sent. When two incidents need the same kind of unit, the dispatch solver plans both together, and its choice is used only if it costs less: for two collisions it may send the far ambulance to the first so that the near one stays free for the second. On 100 random cities its plans cost 17% less than nearest-first (20.39 against 24.63) and match brute force (brain optimise-bench).

Grid cut or signal

A cascade analysis weighs what each grid cut would black out, with a hospital weighted 10, and the shed solver picks the cheapest set of cuts that removes the excess load. A corridor holds the signals on an ambulance’s route at green. A dispatched unit’s unit_status readings close the incident, and an arrest recalls every unit still out.

2.5 Security measures

The Brain treats every input as untrusted until it passes its checks, and every model answer as a proposal that code must verify. Valve and grid calls also need a person’s signed approval. Threats are mapped to MITRE ATT&CK for ICS and, for the AI components, to MITRE ATLAS (docs/SECURITY-MITRE.md).

2.6 Known limitations

  • Joint runs, not yet complete. On 8 November the Brain ran with the Twin team’s Twin and the Guardian team’s Guardian: three incidents end to end, a flood alert. Next: the same through Compose, with the agent teams.
  • The mock Guardian is scripted. T13 and T16 show what the Brain does with a given verdict, not whether a real Guardian would issue it. Next: rerun both with docker-compose.guardian.yml.
  • Tuned on stand-ins. Which sensors move together, and whether sensors in one zone are independent, waits for the real Twin’s data. Next: record a normal day from it (docs/TWIN-HANDOVER.md).
  • TLS and the freshness limit are off by default. Signatures still protect readings and calls. Next: set guardian.tls and twin.max_age_s on the live stack.
  • Guardian alerts are not read. An unreliable actuator reaches the Brain through the containment list, which the gate obeys; a compromised_twin alert does not. Next: read WS /v1/ws/verdicts.
